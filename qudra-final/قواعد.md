## 1. القاعدة الذهبية: لا افتراض، لا اختراع

هذه القاعدة تعلو على أي قاعدة أخرى في هذا الملف.

- **لا تفترض** أي تفصيلة منتج، تصميم، أو تقنية غير موثقة صراحة في: `prototype.html`، `design-system.html`، `README.md`، `dev-handoff.md`، أو هذا الملف.
- إذا لم يكن الشيء موثقاً → **لا تخترعه**. توقف واسأل حسين مباشرة.
- إذا شعرت أنك تُعيد صياغة طلب غامض ليبدو مقبولاً أو آمناً (reframe) → هذا بالضبط إشارة للتوقف والسؤال، وليس سبباً للمتابعة.
- طبّق أسلوب **"Grill Me"**: عند الغموض، اطرح أسئلة استقصائية متتالية عميقة (وليس سؤالاً سطحياً واحداً) حتى تفهم كل تفصيلة — حتى التفاصيل التي قد لا تتوقعها من البداية.
- عند التعارض بين مصدرين: **لا تخترع حلاً وسطاً. لا تستبدل مصدراً بآخر بصمت.** فضّل المصدر الأكثر تحديداً/حداثة عندما تكون النية واضحة، واحفظ السلوك المعروض الحالي (rendered behavior) في حال عدم القدرة على الحسم، ووثّق التعارض في تعليق كود فقط عند الضرورة.

## 2. عقلية المهندس: Coding ≠ Software Engineering

> مصدر هذا القسم: دليل "مهندس البرمجيات" — Yehia Tech (راجع القسم 35 للتفاصيل الكاملة).

الفرق الجوهري ليس في القدرة على كتابة الكود، بل في **نقطة البداية الذهنية**:

| مبرمج ينفّذ فقط | مهندس برمجيات حقيقي |
|---|---|
| "إيه المطلوب؟ وأكتبه إزاي؟" | "إحنا بنحل إيه أصلاً؟ وليه هذا الحل المناسب؟" |
| يبدأ بالتنفيذ مباشرة | يسأل قبل التنفيذ |
| تعريف النجاح: الـ feature اشتغلت والـ tests عدّت | تعريف النجاح: الحل صحيح، قابل للتشغيل، ومناسب للواقع |
| يستخدم الـ AI لتسريع كتابة التنفيذ | يستخدم الـ AI ليسرّع التنفيذ **ثم يراجع** التصميم والنتيجة |
| عند الفشل: يصلّح المشكلة الظاهرة فقط | عند الفشل: يسأل "ليه حصلت؟ وإيه الـ failure mode؟" |
| يفكر لحد تسليم المهمة | يفكر في الإنتاج (Production) والتغيير مع الوقت |

**الفرق الحقيقي مش في الكود نفسه. الفرق في التفكير قبل الكود، والمسؤولية بعد ما يدخل Production.**

قبل أي Feature، اكتب لنفسك أربع إجابات:
1. **المشكلة** — إحنا بنحل إيه أصلاً؟
2. **المستخدم** — لمين؟
3. **معيار النجاح** — إيه اللي يعتبر نجاحاً فعلاً؟
4. **القيود** — إيه القيود اللي لازم الحل يحترمها؟

**لا تتبنَّ حلاً ممتازاً لمشكلة محدش محتاجها.**

## 4. هذه إعادة بناء (Reconstruction) وليست إعادة تصميم (Redesign)

`prototype.html` هو **المرجع البصري والتفاعلي النهائي**. يجب الحفاظ حرفياً على:

- التخطيط (layout) والتسلسل الهرمي (hierarchy)
- المسافات (spacing) والطباعة (typography)
- الألوان، الحدود، البطاقات (cards)
- التنقل (navigation)، الحركات (animations)
- حالات التحميل، الحالات الفارغة، حالات الخطأ
- النوافذ المنبثقة، لوحة الأوامر
- السلوك المتجاوب (responsive)، المظهر الداكن (dark mode)، RTL
- بنية المحتوى وسلوك التفاعل

**ممنوع** إدخال: تخطيطات لوحة تحكم جديدة، مفاهيم تنقل جديدة، بطاقات جديدة، وحدات منتج جديدة، مزايا عمل جديدة، تدفقات عمل جديدة، مفاهيم بيانات جديدة — **إلا** إذا كانت موجودة فعلاً في `prototype.html` أو ملفات المشروع الداعمة.

**إذا لم يكن الشيء محدداً: لا تخترعه.**

## 5. القاعدة البصرية الأهم: Proven مقابل Claimed

> راجع `README.md` القسم 4 لفهم الأساس الفلسفي لهذه القاعدة.

هذا **أهم مكوّن بصري في كامل المنتج** — لا يجوز أبداً تبسيطه أو دمجه:

```typescript
interface TagProps {
  name: string;
  variant: 'proven' | 'claimed';
  evidenceCount?: number;   // يظهر فقط عندما variant === 'proven'
  size?: 'sm' | 'md';
}
```

- **proven**: حد صلب 1px بلون `--accent-line`، خلفية `--accent-soft`، نص بلون `--accent`، عداد الأدلة في فقاعة `.c`
- **claimed**: حد متقطع (dashed) 1px بلون `--line-2`، خلفية شفافة، نص بلون `--ink-3`، **بدون** عداد أدلة إطلاقاً

يجب أن يبقى هذا التمييز ظاهراً بلا استثناء عبر: الملفات الشخصية، صفحات المرشحين، المقارنات، المطابقة، الأدلة، DNA القدرات، وواجهات فجوة المهارة.

## 7. المكدّس التقني (Tech Stack)

ثبّت دوماً **أحدث نسخة مستقرة** من كل حزمة. لا تُثبّت نسخاً قديمة عمداً. لا تستخدم واجهات برمجية (APIs) قديمة أو مهجورة.

### الأساسيات
| المكوّن | التقنية |
|---|---|
| مكتبة الواجهة | React (أحدث نسخة مستقرة) — Concurrent features, Suspense, transitions |
| اللغة | TypeScript (أحدث نسخة، وضع صارم: `strict`, `noImplicitAny`, `strictNullChecks`, exact optional) |
| أداة البناء | Vite (أحدث نسخة) — ESM أصلي، HMR سريع |
| التوجيه | React Router (أحدث نسخة مستقرة) — `createBrowserRouter`, `lazy`, `errorElement` |

### التنسيق (Styling)
- CSS Modules — أنماط خاصة بكل مكوّن/صفحة
- CSS Custom Properties — توكنز التصميم العامة (بدون تكرار)
- **ممنوع تماماً**: Tailwind، Bootstrap، Material UI، Chakra UI، Ant Design، أو أي مكتبة UI عامة جاهزة

### الخطوط (Google Fonts، مع `preconnect` في `index.html`)
| الاستخدام | الخط |
|---|---|
| Display | Readex Pro (400, 500, 700) — من `design-system.html` |
| Body | IBM Plex Sans Arabic (400, 500, 600, 700) |
| Mono | IBM Plex Mono (400, 500) |

### الأيقونات
SVG مضمّن فقط (بأسلوب Lucide، سُمك الخط 1.7–2، `currentColor`). بدون اعتماد وقت تشغيل على مكتبة أيقونات خارجية. لفّها في مكوّن `<Icon>` مع `aria-hidden` + `title` للوصولية.

### الاختبار (البنية فقط في B0، لا يُطلب Test Suite كامل بعد)
Vitest + React Testing Library + jsdom

### الفحص الثابت (Linting)
ESLint (أحدث) + typescript-eslint — بدون متغيرات غير مستخدمة، بدون `any`، بدون إرجاعات ضمنية غير واضحة.

## 9. معنى Clean Code هنا تحديداً

الكود النظيف متطلب أساسي وليس اختيارياً. يجب أن يفهمه مهندس آخر بدون الحاجة لإعادة هندسته عكسياً (reverse-engineer).

### تجنّب دائماً
- مكوّنات عملاقة (giant components)، `App.tsx` ضخم
- تكرار JSX، تكرار CSS، تكرار منطق العمل
- أرقام سحرية (magic numbers)، ثوابت غير مشروحة
- حالة قابلة للتغيير عامة (global mutable state)
- تلاعب مباشر بالـ DOM، `innerHTML`
- معالجات أحداث نصية (string-based)، `onclick` مضمّن
- Prop drilling مفرط
- تبعيات (dependencies) غير ضرورية
- تجريدات غير ضرورية (over-engineering)
- تنفيذات Backend وهمية (fake backend)
- استدعاءات API مباشرة داخل مكونات العرض (presentational components)
- قواعد عمل (business rules) داخل JSX

### فضّل دائماً
- مسؤولية واحدة لكل وحدة (Single Responsibility)
- التركيب (Composition) على الوراثة
- واجهات مُنمّطة (typed interfaces)
- حالة قابلة للتنبؤ (predictable state)
- مكونات قابلة لإعادة الاستخدام
- معمارية موجهة بالميزة (feature-oriented)
- حدود خدمة واضحة (clear service boundaries)
- نماذج بيانات صريحة
- HTML دلالي (semantic)
- وحدات صغيرة ومركّزة
- منطق قابل للاختبار
- عزل التبعيات

**لا تخلط بين "معمارية نظيفة" و"إفراط هندسي". المعمارية يجب أن تكون: بسيطة + قابلة للقراءة + معيارية (Modular) + قابلة للتوسع، في آنٍ واحد.**

## 10. التعليقات داخل الكود (Code Comments)

**قاعدة إلزامية صريحة من حسين:** عند كتابة أي كود، ضع تعليقات واضحة تشرح:
- الغرض من كل ملف/مكوّن في بدايته (ماذا يفعل، ولماذا وُجد)
- الغرض من كل دالة/hook غير بديهية
- أي منطق عمل (business logic) معقّد أو غير واضح من القراءة السريعة
- أي قرار هندسي غير بديهي (لماذا اخترنا هذا الأسلوب وليس غيره)

**الهدف**: تسهيل القراءة والتعديل المستقبلي، سواء من حسين نفسه أو من وكيل ذكاء اصطناعي آخر (Claude Code، Cursor) ينتقل للعمل على المشروع لاحقاً بدون سياق سابق.

لا تُفرط في التعليقات البديهية (مثل `// increment i by 1` فوق `i++`) — التعليق يجب أن يضيف قيمة حقيقية للفهم، لا أن يكرر ما يقوله الكود نفسه بوضوح.

## 19. الأولوية لـ RTL

QUDRA منتج RTL أولاً (RTL-first)، وليس LTR مع انعكاس لاحق.

- استخدم `dir="rtl"` على مستوى المستند/التطبيق.
- استخدم خصائص CSS المنطقية (logical properties): `padding-inline`, `margin-inline`, `inset-inline`, `border-inline-start`, `border-inline-end`.
- **تجنّب** الخصائص الاتجاهية الفيزيائية (`padding-left/right`) حيث توجد مكافئات منطقية مناسبة.
- **لا تبنِ** LTR أولاً ثم تعكسه لاحقاً.

تحقّق من سلوك RTL الصحيح في: التنقل، البطاقات، النماذج، التقدّم (progress)، الرسوم البيانية، الجداول الزمنية، الجداول، النوافذ المنبثقة، الأسهم، الأيقونات، الشارات، الأرقام، المصطلحات التقنية. **اختبر كل مكوّن في RTL قبل اعتباره منتهياً.**

## 22. إدارة الحالة (State Management)

**لا تُدخل** Redux أو أي مكتبة حالة عامة أخرى لـ B0 إلا إذا احتاج التطبيق ذلك فعلياً بشكل حقيقي.

استخدم:
- حالة React محلية للواجهة المحلية
- حالة الميزة (feature state) للسلوك الخاص بميزة محددة
- Context فقط للحالة المشتركة فعلياً على مستوى التطبيق

**مرشحون جيدون لـ Context**: المظهر (theme)، الدور (role)، تدفق المشكلة الحالي، حالة المحاكاة إذا كانت مشتركة بين المحاكاة والتقييم.

**ممنوع** وضع كل قيمة حالة تطبيق داخل Context. **لا تُحوّل** Context إلى مكب عام (global dumping ground).

---

## 23. المظهر الليلي (Theme)

نفّذ نظام المظهر الخاص بالـ prototype. استخدم `data-theme="dark"` على عنصر HTML الجذر. احفظ المظهر باستخدام اصطلاح تخزين المظهر الموجود في QUDRA. احترم تفضيل النظام عند عدم وجود تفضيل محفوظ صراحة. **لا تُكرر** المكونات للمظهر الفاتح والداكن — استخدم التوكنز.

---

## 24. التصميم المتجاوب (Responsive)

حافظ على السلوك المتجاوب للـ prototype. دعم: موبايل، تابلت، ديسكتوب. استخدم نقاط التوقف (breakpoints) المحددة في الـ prototype/design-system حيثما ينطبق ذلك. **لا تُنشئ** منتجاً موبايل منفصلاً بالكامل — استخدم نفس معمارية المكونات بشكل متجاوب.

تأكد من: عدم وجود انسياب أفقي (horizontal overflow)، طباعة قابلة للقراءة، عناصر تحكم قابلة للاستخدام، أهداف لمس يمكن الوصول إليها، سلوك BottomNav صحيح، تكديس البطاقات الصحيح، سلوك الشبكة (grid) الصحيح.

---

## 25. الوصولية (Accessibility)

الوصولية متطلب من الدرجة الأولى، ليست إضافة لاحقة. نفّذ:

HTML دلالي، تنقل بلوحة المفاتيح، حالات تركيز مرئية، `:focus-visible`، تسميات قابلة للوصول، دلالات أزرار صحيحة، تسميات نماذج قابلة للوصول، حوارات قابلة للوصول، فخّ تركيز حيث يلزم، استعادة التركيز، `aria-current`، `aria-live`، دعم تقليل الحركة (`prefers-reduced-motion`).

نفّذ رابط "تخطي إلى المحتوى" (skip-to-content). الأزرار ذات الأيقونة فقط يجب أن تملك تسميات قابلة للوصول. **لا تُضِف** خصائص ARIA بلا داعٍ — استخدم العناصر الدلالية الأصلية حيثما أمكن.

---

## 26. لوحة الأوامر (Command Palette)

أعِد بناء لوحة الأوامر الحالية في QUDRA كمكوّن React حقيقي. يدعم:

اختصار لوحة المفاتيح (Ctrl+K / Cmd+K)، البحث، المطابقة الضبابية (fuzzy matching)، التنقل بلوحة المفاتيح (ArrowUp/ArrowDown)، Enter، Escape، إدارة التركيز، دلالات حوار قابلة للوصول.

يحتوي الـ prototype على قائمة محددة من الشاشات القابلة للتنقل ومداخل الأوامر — **احفظ** تلك المعلومة بدلاً من اختراع نظام أوامر جديد.

---

## 27. النوافذ المنبثقة (Modals)

نفّذ الحوارات كمكونات React قابلة لإعادة الاستخدام. السلوك المطلوب: فخّ تركيز، Escape للإغلاق، خلفية (backdrop)، إدارة تمرير الجسم، استعادة التركيز، اسم قابل للوصول، سلوك لوحة مفاتيح صحيح. **لا تستخدم** مكتبة نوافذ منبثقة خارجية ضخمة.

---

## 28. حالات التحميل (Loading States)

حافظ على سلوك التحميل المصمّم في الـ prototype. **لا تستبدل** تجارب تحميل ذات معنى بمؤشرات دوران عامة. يستخدم الـ prototype صراحة هياكل هيكلية (skeletons) وتحميلاً مرحلياً (staged loading). أنشئ مكونات تحميل قابلة لإعادة الاستخدام تدعم: الهياكل العظمية (skeletons)، التقدّم، التحليل المرحلي، الإجراءات المعطّلة، أزرار التحميل.

**تفاصيل من مواصفة بولت**: أبداً لا تستخدم مؤشر دوران شامل للصفحة الكاملة. كل شاشة لها هيكل عظمي يطابق تخطيطها. تقدّم التحليل المرحلي: 6 خطوات مسمّاة بتقدّم بصري. تحميل الزر: مؤشر دوران داخلي، معطّل، مع الحفاظ على العرض. حركة الوميض الهيكلي: خطي 1.5 ثانية لا نهائي. استخدم React Suspense لحدود المسارات مع بديل هيكلي.

---

## 29. الحالات الفارغة (Empty States)

حافظ على الحالات الفارغة المقصودة في المنتج. البيانات الفارغة ليست خطأً تلقائياً. ملف أدلة فارغ يجب أن يشرح:
1. ما الناقص
2. لماذا هو مهم
3. ما الذي يستطيع المستخدم فعله الآن

**لا تُظهر** حاويات فارغة بلا معنى. استخدم لون التركوازي للإجراءات، وليس الأحمر — الفراغ ليس فشلاً، بل دعوة.

---

## 30. حالات الخطأ (Error States)

يجب أن تكون الأخطاء متمايزة بصرياً ودلالياً عن الفجوات (Gaps). نفّذ سلوك تعافٍ ذا معنى لـ: فشل التحليل، فشل الطلبات، إدخال غير صحيح، فشل الشبكة، محتوى غير متاح. استخدم الأحمر **فقط** للأخطاء الحقيقية/حالات الهدم الفعلية.

تفاصيل من مواصفة بولت: أخطاء الحقول تظهر مضمّنة (inline) أسفل الحقل مباشرة، وليس كـ toast. أخطاء النظام تظهر كـ toast من الأسفل، تختفي تلقائياً بعد 5 ثواني، مع إمكانية إغلاق يدوي. أخطاء API تظهر مضمّنة مع زر إعادة محاولة.

---

## 31. المحاكاة العملية (Simulation)

يجب تنفيذ المحاكاة العملية بحالة React (React state). يجب أن تدعم السلوك الممثَّل في الـ prototype: تقدّم المهام، المهمة الحالية، الإجابات، السابق/التالي، المؤقت، التسليم، التقييم، التقدّم، حماية الخروج حيث تكون ممثَّلة.

**ممنوع استخدام**: `document.getElementById`، `querySelector` لحالة التطبيق، `innerHTML`، مصفوفات عامة قابلة للتغيير كحالة، معالجات أحداث نصية. **React يملك حالة الواجهة، لا شيء آخر.**

---

## 32. التقييم (Evaluation)

حافظ على شاشة التقييم. يجب أن تدعم: درجة متحركة، معايير، نقاط قوة، نقاط ضعف، تفصيل المهام، إعلان الوصولية لتغيّرات الدرجة (`aria-live`). تقييم الـ prototype ليس مجرد رقم — إنه يشرح النتيجة. **لا تُختزل** إلى بطاقة درجة عامة.

---

## 33. المطابقة القابلة للتفسير

المطابقة يجب أن تبقى قابلة للتفسير دائماً. **لا تعرض أبداً** نسبة مئوية بدون سياق. يجب أن تستطيع بطاقة مطابقة المرشح كشف: درجة المطابقة، القدرات ذات الصلة، الأدلة الداعمة، المشاريع ذات الصلة، الأسباب، الفجوات.

منطق المنتج:
```
Problem → Required Capability → Evidence → Candidate → Explanation
```
**وليس**:
```
Candidate → arbitrary AI score
```

---

## 34. معمارية الأدلة (Evidence Architecture)

يجب معاملة الأدلة ككيان نطاق (domain concept) من الدرجة الأولى. يجب على الواجهة الحفاظ على معلومات مثل: المصدر، النوع، المهارة، التاريخ، التحقق، الوزن/القوة، الصلة، الصعوبة، النتيجة.

يحتوي الـ prototype فعلاً على مصادر أدلة متعددة (GitHub، مشاريع، تحديات، تقييمات، ادعاءات). **لا تُسطّحها** إلى قائمة مهارات عامة.

### تقادم الأدلة (Evidence Decay)

يجب أن تظل معمارية الواجهة الأمامية متوافقة مع تقادم الأدلة مع الوقت. **لا تحسب وتخزّن** نتيجة تقادم وهمية بشكل دائم في الواجهة. طبقة التقييم المستقبلية يجب أن تكون قادرة على حساب الحداثة/التقادم ديناميكياً. الواجهة الأمامية تستهلك فقط بيانات النطاق الناتجة.

---

## 35. مبادئ هندسة البرمجيات (من دليل يحيى تِك)

> هذا القسم يلخّص المبادئ الأساسية من دليل "مهندس البرمجيات" الذي يجب أن يوجّه تفكير الوكيل **قبل** كتابة أي كود، وليس فقط أثناءه.

### الأسس الثمانية التي يجب التفكير فيها قبل أي Feature

| # | المجال | السؤال الجوهري |
|---|---|---|
| 1 | Problem & Requirements | إحنا بنحل إيه؟ لمين؟ وإيه القيود اللي لازم الحل يحترمها؟ |
| 2 | System Design | النظام يتقسم إزاي؟ وإيه الـ boundaries والـ trade-offs المناسبة؟ |
| 3 | Data & Databases | البيانات شكلها إيه؟ وإزاي نخزّنها ونغيّرها من غير ما نفقد صحتها؟ |
| 4 | Reliability | إيه اللي يحصل لو dependency وقعت؟ والـ request اتكررت، أو حمل النظام زاد؟ |
| 5 | Security | مين مسموح له يعمل إيه؟ وإزاي نحمي البيانات والـ secrets؟ |
| 6 | Performance & Cost | الحل سريع كفاية؟ ينفع يكبر؟ وبتكلفة منطقية؟ |
| 7 | Production Engineering | بعد الـ deploy، هنعرف منين إن النظام شغال ونفهم سبب أي مشكلة؟ |
| 8 | Testing & Change | هل نقدر نغيّر النظام ونطلق نسخ جديدة من غير ما نكسر الموجود؟ |

### System Design ليس رسمة Interview

قبل التنفيذ اسأل: فين الـ boundaries؟ إيه الـ bottleneck المتوقع؟ إيه أبسط تصميم يكفي دلوقتي؟ إيه القرار اللي هيكون غالي تغييره بعدين؟

**صمّم لاحتياج النهارده، بس خليه سهل يتوسّع ويتغيّر بعدين من غير Refactoring كبير.**

### Data & Databases

البيانات هي حالة النظام (System State). أي قرار غلط في الـ Data Model ممكن يبقى تغييره مؤلماً بعدين ويتطلب Migrations صعبة. خذ وقتك قبل أي تغيير في شكل البيانات.

### Reliability — الـ Happy Path مش هو الـ Production

السؤال الهندسي: لو جزء من النظام فشل، هل باقي التجربة تفضل مفهومة؟ هل نقدر نعيد المحاولة من غير ما نكرر أثر العملية (**Idempotency**)؟ الفشل مش هتمنعه 100%، لكن دور على الـ failure modes والـ edge cases بدري عشان تقلل احتماله وتأثيره قبل ما يوصل للمستخدم.

### Security ليست Feature تُضاف في الآخر — هي جزء من التصميم

مش مطلوب كل مهندس يكون Security Specialist، لكن أي مهندس لازم يعرف يبني Defaults آمنة ويفهم المخاطر الأساسية: Authentication/Authorization، Least privilege، Validation، حماية البيانات والـ secrets، مخاطر الويب الأساسية (OWASP، Injection، Session risks).

### Performance & Cost

الأداء قرار تقني واقتصادي: أسرع أو أرخص — من غير تعقيد مالوش لازمة. حدّد الـ bottleneck الحقيقي قبل أي optimization. قِس الأداء قبل التغيير وبعده. قيّم هل التحسّن يبرر التعقيد والتكلفة الإضافية.

### Production Engineering — الـ Deploy بداية مسؤولية جديدة

بعد الـ deploy، لازم تعرف تجاوب: حصل إيه؟ لمين؟ من إمتى؟ فين؟ وإيه الدليل اللي يثبت السبب بدل التخمين؟ القيمة: لما يحصل Incident، تقلّل وقت التخمين وتوصل للسبب أسرع (Observability، Logging، Metrics، Monitoring، Alerting).

### Testing & Change

هدف الـ Tests ليس فقط إثبات إن الكود شغال النهاردة — قيمتها الأكبر إنها تخليك تغيّره بكرة بثقة أعلى. الهندسة الجيدة تقلّل تكلفة التغيير.

### دور الذكاء الاصطناعي مقابل دور المهندس (جدول حاسم)

| المجال | الـ AI يسرّع | المهندس يمتلك |
|---|---|---|
| Problem | تلخيص Context وصياغة أسئلة | تحديد المشكلة اللي تستحق الحل |
| Architecture | اقتراح Designs وبدائل | اختيار الـ Trade-offs المناسبة |
| Data | Schemas وQueries وMigrations | صحة الـ Model والـ Consistency |
| Reliability/Security | اقتراح Tests ومخاطر محتملة | تقدير الخطر والقرار النهائي |
| Production | تحليل Logs وشرح Signals | Incident judgment والمسؤولية |
| Testing | توليد Test cases بسرعة | تحديد إيه اللي لازم يتختبر فعلاً |

**كل ما الـ AI يسرّع التنفيذ، قيمة الـ Engineering Judgment (حكم المهندس) بتزيد.** الترتيب الصحيح دائماً: `Engineer frames → AI accelerates → Engineer validates → Production feedback`.

### قائمة فحص المهندس (طبّقها قبل كل Feature)

**قبل ما تكتب الكود:**
- إحنا بنحل إيه؟ ومين المستخدم؟
- إيه الـ constraints والـ success criteria؟
- إيه أبسط Design مناسب دلوقتي؟
- البيانات شكلها إيه؟ وإيه الـ consistency المطلوبة؟

**قبل الـ Deploy:**
- إيه الـ security risk والـ permissions؟
- إيه اللي ممكن يفشل؟ وهل العملية Idempotent؟
- الـ scale والـ latency والـ cost مقبولين؟
- هل الـ tests بتحمي أهم behavior؟

**بعد الـ Deploy:**
- لو حصل Incident، هل عندنا Logs/Metrics كفاية؟
- هنعرف منين إن النظام شغال فعلاً؟

**أي سؤال مش عارف تجاوبه = موضوع دراسة أو Experiment حقيقي، مش تخمين.**

## 36. الأمان (Security)

حتى في مرحلة B0 (بيانات تجريبية، بدون Backend حقيقي)، ابنِ بعقلية أمان صحيحة منذ البداية بحيث لا تحتاج إعادة هيكلة لاحقاً:

- **Identity & Access**: صمّم واجهات الأدوار (Role: صاحب مشكلة/مستخدم) بحيث تكون منطقة التحقق من الصلاحيات معزولة (Context/hook مخصص)، وليست مبعثرة داخل المكونات.
- **Input & Data**: أي حقل إدخال (مثل `ProblemInputPage`) يجب أن يحتوي تحققاً من صحة الإدخال (Validation) من جهة الواجهة، حتى لو كانت البيانات لا تُرسَل لخادم حقيقي بعد.
- **Secrets**: لا تضع أبداً أي مفتاح API أو سر حقيقي داخل كود الواجهة الأمامية، حتى في مرحلة Mock. استخدم متغيرات بيئة (`.env`) مع placeholders واضحة.
- **Least Privilege بصرياً**: تأكد أن واجهة "صاحب المشكلة" لا تعرض بيانات/إجراءات مخصصة لواجهة "المرشح" وبالعكس، حتى في نسخة Demo.

---

## 37. الموثوقية والفشل (Reliability & Failure)

طبّق مبدأ "الـ Happy Path مش هو الـ Production" حتى على مستوى الواجهة الأمامية في B0:

- كل عملية تحليل/محاكاة/تحميل يجب أن تملك مسار فشل مصمَّم (وليس فقط مسار نجاح)، حتى لو كانت البيانات Mock حالياً (مثال: ماذا يحدث لو "فشل" تحليل GitHub الوهمي؟ يجب أن تكون هناك حالة خطأ مصمَّمة له مسبقاً في `services/`).
- عمليات مثل "إرسال الإجابة" في `Simulation` يجب أن تُصمَّم بمبدأ **Idempotency** منذ البداية: النقر على "إرسال" مرتين لا يجب أن يُكرر أثر العملية.
- استخدم `useTimer` وhooks التنظيف (`cleanup`) بعناية لتفادي تسريبات الذاكرة (memory leaks) عند تفكيك المكونات (unmount).

---

## 38. الأداء والتكلفة (Performance & Cost)

- استخدم Lazy loading للمسارات الرئيسية (`React.lazy` + `Suspense`) — لا حاجة لتحميل كل صفحات المنتج (18+ شاشة) دفعة واحدة عند الدخول للصفحة الرئيسية.
- تجنّب إعادة الحساب غير الضرورية (استخدم `useMemo`/`useCallback` بحكمة، وليس بإفراط بلا داعٍ حقيقي — الإفراط في التحسين المبكر هو أيضاً خطأ هندسي).
- الصور والأيقونات: استخدم SVG مضمّن بدل الصور الرقمية حيثما أمكن لتقليل الطلبات الشبكية.
- لا تُضِف مكتبات رسوم بيانية (chart libraries) ضخمة إذا كان SVG/CSS بسيط يكفي (مثال: `CapabilityDNA` و`Ring` يُبنيان بـ SVG مباشر، وليس بمكتبة خارجية).

---

## 39. الاختبار والتغيير (Testing & Change)

- البنية الأساسية لـ Vitest + React Testing Library يجب أن تكون جاهزة من بداية B0 (حتى لو لم تُكتب تغطية اختبار شاملة بعد).
- أي منطق عمل (business logic) معقّد (مثل حساب `MatchScore` أو حالة `SimContext`) يجب أن يكون **قابلاً للاختبار بمعزل عن الواجهة** (hook/دالة منفصلة يمكن اختبارها بدون تركيب مكوّن React كامل).
- عند أي تعديل مستقبلي، تأكد أن السلوك الحالي المصمَّم (rendered behavior) لا ينكسر — هذا هو معيار "التغيير الآمن" المذكور في قسم 35.

## 40. دور الذكاء الاصطناعي في التنفيذ

طبّق الجدول الوارد في القسم 35 حرفياً أثناء تنفيذك كوكيل ذكاء اصطناعي على هذا المشروع تحديداً:

- الـ AI (أنت، الوكيل المنفّذ) يُسرّع: توليد الكود، اقتراح تصميمات المكونات، توليد بيانات Demo، شرح الأخطاء.
- **حسين (المهندس/صاحب القرار) يمتلك**: تحديد ما إذا كانت هناك حاجة فعلية للـ feature، اختيار الـ Trade-offs المعمارية الكبرى، الحكم النهائي على الجودة، قرار الانتقال بين المراحل (B0→B1→B2).
- **لا تتخذ قرارات معمارية كبرى بصمت** (مثل تغيير بنية المجلدات، إضافة مكتبة جديدة، تغيير استراتيجية إدارة الحالة) — اعرضها كخيار مع تبرير، ودع القرار النهائي لحسين.

## 41. نظام المهارات (Skills System) — إلزامي قبل كل مهمة

> **قاعدة إلزامية صريحة من حسين، لا استثناء لها.**

قبل البدء في **أي مهمة أو مشروع**، يجب على الوكيل:

1. **فحص المهارات المتاحة أولاً**: استخدم مهارة `find-skills` (من [commandcode.ai/skills](https://commandcode.ai/skills)) لتحديد أي مهارة مُتخصصة موجودة تناسب المهمة المطلوبة تحديداً، وحمّلها/فعّلها قبل التنفيذ.
2. **راجع الملف المحلي `SKILLS.md`** الموجود في جذر هذا المشروع كخط أمان — يحتوي محتوى المهارات الأساسية المستخدمة دائماً، بحيث يعمل حتى لو تعذّر تحميل مهارة خارجية فعلياً.
3. **عند أي غموض أو تفصيلة غير واضحة في المشروع** (سواء منتج، تصميم، أو تقنية): استخدم أسلوب مهارة **"Grill Me"** ([المصدر](https://awesomeskill.ai/skill/julianoczkowski-designer-skills-grill-me)) — اطرح أسئلة استقصائية متتالية عميقة حتى تصل لفهم كامل، بدل الافتراض. هذا يشمل تفاصيل قد لا تتوقع أنك بحاجة للسؤال عنها من البداية.
4. مصادر إضافية للمهارات عند الحاجة: [skills.sh](https://www.skills.sh/) (يحتوي كذلك مهارة `find-skills` مكافئة).

**ملاحظة تقنية مهمة**: نظام تحميل المهارات (`npx skills add <repo> --skill <name>` أو ما يعادله) هو معيار مفتوح (Agent Skills spec) مدعوم في عشرات أدوات الذكاء الاصطناعي البرمجية. تم التحقق فعلياً أن Bolt.new قادر على تحميل هذه المهارات بنجاح. **بغض النظر عن الأداة المستخدمة**، يبقى ملف `SKILLS.md` المحلي في هذا المشروع مرجعاً احتياطياً مضموناً في كل الأحوال.

## 44. نظام الذاكرة على مستوى المشروع

بالإضافة لملفات التتبع التقليدية (TASKS/STATUS/DECISIONS/CHANGELOG)، يحتفظ هذا المشروع بمجلد `.memory/` مخصص لتفاصيل أدق يحتاجها أي وكيل ذكاء اصطناعي يبدأ العمل من نقطة صفر بدون سياق سابق:

```
.memory/
├── decisions.md    ← قرارات معمارية دقيقة (أعمق تفصيلاً من DECISIONS.md العام)
├── glossary.md      ← قاموس مصطلحات QUDRA (Evidence, Capability, Proven/Claimed...)
└── notes.md          ← ملاحظات عمل متفرقة، أفكار قيد التقييم، تحذيرات مؤقتة
```

**بروتوكول الاستخدام:**
1. في **بداية** أي جلسة عمل جديدة على المشروع، اقرأ `.memory/glossary.md` أولاً للتأكد من فهم مصطلحات المنتج بدقة قبل أي تنفيذ.
2. عند اتخاذ **أي قرار معماري** غير موثق مسبقاً (مثل: "قررنا استخدام `useReducer` بدل `useState` المتعدد في `SimContext` لأن..."), وثّقه في `.memory/decisions.md` فوراً، وليس بعد انتهاء الجلسة.
3. لا تخزّن في `.memory/` أي بيانات حساسة (مفاتيح API، أسرار، بيانات مستخدمين حقيقية).
4. هذا المجلد **entry point مختصر** له في جذر المشروع عبر ملف `AGENTS.md` (راجع القسم 20 في `README.md`) الذي يوجّه أي وكيل جديد فوراً لأين يجد كل شيء دون الحاجة لقراءة كل الملفات من الصفر.

### `PROJECT_MAP.md` — الخريطة التفصيلية لكل ملف كود (إلزامية)

بالإضافة لـ `.memory/`، يحتفظ المشروع بملف `PROJECT_MAP.md` في الجذر — وهو **مرجع مختلف الغرض** عن `.memory/`: بينما `.memory/` يوثّق قرارات ومصطلحات عامة، `PROJECT_MAP.md` يوثّق **كل ملف كود على حدة**: ماذا يفعل بالتفصيل، وما محتواه، وكيف يرتبط بالملفات الأخرى (يستورد من/يُستخدم من قبل/مرتبط بـ Route/مرتبط بـ Context).

**قاعدة الصيانة الإلزامية**: لا يُغلق أي Task يتضمن ملفاً جديداً أو تعديلاً جوهرياً على ملف موجود دون تحديث `PROJECT_MAP.md` بنفس القسم المقابل. هذا الملف يُعامَل بنفس إلزامية `TASKS.md` تماماً — إغفاله يعني أن الـ Task غير مكتمل. راجع `PROJECT_MAP.md` نفسه لمعرفة الصيغة الدقيقة المطلوبة لكل إدخال، وراجع `QUDRA_FINAL_BOLT_PROMPT.md` (القسم الخاص بالـ Tracking) للتفاصيل التنفيذية الكاملة.

**الهدف العملي**: عندما يحتاج حسين (أو أي وكيل آخر) لتعديل ميزة معينة لاحقاً، يفتح `PROJECT_MAP.md` أولاً بدل البحث في كامل شجرة المشروع، ويعرف فوراً أي ملف يحتوي الميزة المطلوبة وماذا يفعل بالتحديد وما تأثير تعديله على باقي النظام.

## 46. عقد تنفيذ إضافي للوكيل — منع الادّعاء الكاذب

> **لا تفترض. لا تخترع. افحص الموجود أولاً. استخدم Find-Skills قبل التنفيذ. استخدم Grill-Me عند الغموض. نفّذ بأبسط بنية قابلة للتوسع، ثم اختبر كالمستخدم، وتحقق كأدمن، ووثّق كل شيء قبل إعلان الإنجاز.**

### لا تدّعِ ما لم تفعله

ممنوع كتابة أي من هذه العبارات في تقرير أو تعليق كود **إلا** إذا تم تنفيذ التحقق فعلياً ووُجد دليل موثّق في `TEST_REPORT.md`:

- `100% verified`
- `production ready`
- `fully tested`

هذه العبارات تُعامَل كادّعاء كاذب (False Completion) إذا لم يوجد دليل فعلي يدعمها — وهذا انتهاك مباشر لقاعدة "الحل صحيح وموثّق فعلاً" الموضحة في القسم 2 من هذا الملف.

### لا تترك Dead UI (واجهة بلا سلوك حقيقي)

أي زر، رابط، تبويب (tab)، نافذة منبثقة (modal)، أمر (command)، نموذج (form)، أو عنصر تنقل (navigation) يُضاف للواجهة **يجب أن يملك سلوكاً حقيقياً** داخل حدود المرحلة الحالية — وليس عنصراً تجميلياً بلا وظيفة.

إذا كان السلوك الكامل يعتمد على Backend لم يُبنَ بعد (مستقبلي): أنشئ حد خدمة/Mock واضح (`services/`) بدل بناء "Backend وهمي" يُضلِّل القارئ بأنه حقيقي.

### التوثيق بعد كل Task — بروتوكول موسَّع

بالإضافة لما هو موصوف في القسم 43 أعلاه، بعد كل مهمة:

1. حدّث `TASKS.md`
2. حدّث `STATUS.md`
3. حدّث `CHANGELOG.md`
4. حدّث `DECISIONS.md` عند اتخاذ قرار جديد
5. **أنشئ ملف تفصيلي جديد**: `.memory/tasks/YYYY-MM-DD_<TASK-ID>.md` بالصيغة التالية:

```markdown
# Task

## Goal
## Context
## Skills Used
## Changes
## Tests
## Admin/User Verification
## Security Review
## What Was Not Verified
## Decisions
## Next Step
```

6. سجّل المهارات (Skills) المستخدمة ونتيجة تحميلها الفعلية (نجح/فشل).
7. سجّل بوضوح تام ما تم اختباره فعلياً وما **لم** يتم اختباره — القسم `What Was Not Verified` إلزامي وليس اختيارياً، حتى لو كانت القائمة فارغة (اكتب "لا يوجد" صراحة بدل حذف القسم).

### Browser/Admin Verification — شرط التنفيذ الفعلي

إذا كانت أداة تصفح (Browser tool) متاحة فعلياً في بيئة التنفيذ:
- نفّذ الاختبار فعلياً، لا تصفه نظرياً.
- سجّل دخول Admin/Test User عند توفر حساب/بيئة مناسبة.
- جرّب كل زر وتفاعل جديد فعلياً.
- تحقق من: التنقل (navigation)، الحالة (state)، الترابط (integration)، الـ console، والشبكة (network) عند الحاجة.

إذا لم تكن الأداة متاحة:
- **لا تدّعِ أنك اختبرت المتصفح.**
- نفّذ أقصى تحقق آلي ممكن (typecheck, lint, build).
- اكتب بوضوح تام في `TEST_REPORT.md` ما بقي غير متحقق منه فعلياً.

## 47. قاعدة التطوير المستقبلي — قابلية الاستبدال دون إعادة كتابة

كل كود يُكتب في B0 يجب أن يكون قابلاً لاستبدال مصدر بياناته:

```
mock service → real API
```

**دون إعادة كتابة الصفحات أو مكونات العرض (presentational components) المرتبطة به.**

هذا يعني عملياً: أي مكوّن أو صفحة يستهلك بيانات، يجب أن يستهلكها عبر دالة خدمة (`service function`) محدَّدة الشكل (Interface/Type واضح)، وليس عبر منطق جلب بيانات مباشر داخل المكوّن نفسه.

**لا تبنِ تجريداً (abstraction) مبالغاً فيه** يضيف طبقات غير ضرورية "تحسباً" لسيناريوهات لم تُطلَب بعد؛ ابنِ حدوداً (boundaries) واضحة وكافية فقط لجعل الانتقال للنسخة التالية (B1) ممكناً دون تدمير الأساس الحالي. التوازن بين الحالتين (لا نقص في الحدود / لا إفراط في التجريد) هو بالضبط ما يفرّق "معمارية نظيفة" عن "إفراط هندسي" (راجع القسم 9).
