## 1. find-skills — إيجاد المهارة المناسبة (إلزامية قبل كل مهمة)

**الغرض**: قبل تنفيذ أي مهمة (كبيرة أو صغيرة)، افحص أولاً ما إذا كانت هناك مهارة متخصصة تجعل نتيجة هذه المهمة تحديداً أفضل، بدلاً من الاعتماد على معرفة عامة فقط.

### كيف تُطبَّق عملياً

1. **افهم المهمة المطلوبة بدقة أولاً** — ما هو نوعها فعلياً؟ (كتابة كود React، تصميم واجهة، كتابة توثيق، تحليل بيانات، إلخ)
2. **نفّذ الأمر فعلياً عبر الـTerminal** (Bolt.new يدعم تنفيذ أوامر npx فعلياً):
   ```bash
   npx skills find <keyword>
   ```
   استخدم كلمات مفتاحية دقيقة مشتقة من المهمة نفسها (وليس كلمات عامة). مثال: `npx skills find "react hooks"` وليس `npx skills find react` فقط.
3. **إذا وُجدت مهارة مناسبة**: ثبّتها فعلياً عبر:
   ```bash
   npx skills add <owner>/<repo> --skill <skill-name> --agent claude-code
   ```
4. **إذا لم توجد مهارة مطابقة تماماً، أو فشل الأمر لأي سبب تقني**: انتقل مباشرة لتنفيذ المهمة بالاعتماد على `قواعد.md` كمرجع، دون تأخير، وسجّل سبب عدم التثبيت.
5. **لا تتوقف عند هذه الخطوة أكثر من اللازم** — الهدف تحسين جودة النتيجة، وليس تعطيل سير العمل بحثاً عن مهارة قد لا تكون ضرورية.
6. **لا تدّعِ تنفيذ أمر لم يُنفَّذ فعلياً.** إذا لم يكن الـTerminal متاحاً أو فشل الأمر، صرّح بذلك صراحة بدل الادعاء بنتيجة بحث وهمية.

### حدود البحث عن المهارات (إلزامي — لمنع الحلقات اللانهائية)

- **الحد الأقصى المطلق: 10 مهارات لكل مهمة واحدة.** بعد الوصول لهذا العدد، توقف عن أي بحث إضافي فوراً بغض النظر عن النتيجة، وانتقل للتنفيذ بما هو متوفر.
- **تثبيت نتيجة واحدة فقط لكل بحث:** عند تنفيذ `npx skills find` لأي كلمة مفتاحية، لا تُثبّت (`npx skills add`) إلا **أعلى نتيجة واحدة فقط** من حيث عدد التثبيتات (installs) الظاهر في نتائج البحث — وليس أكثر من مهارة واحدة لكل كلمة بحث، ومهما كانت النتائج الأخرى مغرية. إذا كانت المهارة الأعلى تقييماً موجودة بالفعل (مثبّتة من محاولة سابقة)، لا تُثبّت غيرها إطلاقاً لنفس الغرض.
- **لا تُكرّر نفس عملية البحث (نفس الكلمة المفتاحية أو ما يقاربها) أكثر من مرة واحدة.** إذا فشل أو لم يُرجع نتيجة مفيدة، جرّب كلمة مفتاحية مختلفة جوهرياً مرة واحدة فقط، ثم توقف.
- **إذا لاحظت أن نفس الرسالة (مثل "Fetching skills") تتكرر أكثر من 5 مرات متتالية دون تغيّر فعلي في النتيجة، هذا مؤشر على حلقة عالقة (stuck loop) — أوقف العملية فوراً بنفسك ولا تنتظر تدخل المستخدم.**
- **الهدف من find-skills هو تسريع وتحسين جودة التنفيذ، وليس استنفاد وقت الجلسة في البحث.** مهمة واحدة تحتاج عادة مهارة واحدة إلى ثلاث مهارات مطابقة فعلياً، وليس عشرات المحاولات.
- عند الوصول للحد الأقصى (10) أو اكتشاف حلقة عالقة، اعتمد مباشرة على قواعد.md وSKILLS.md نفسه كمرجع كافٍ، وابدأ التنفيذ.

### أمثلة على مهام QUDRA ومتى تبحث عن مهارة مطابقة

| نوع المهمة في QUDRA | ابحث عن مهارة متعلقة بـ |
|---|---|
| بناء مكوّن React جديد (`Ring`, `Tag`, `EvidenceCard`) | React best practices، Component design patterns |
| كتابة CSS Modules للتوكنز | CSS architecture، Design systems |
| إعداد التوجيه (routing) | React Router patterns |
| كتابة/مراجعة كود TypeScript صارم | TypeScript strict mode، Type safety |
| مراجعة الوصولية (Accessibility) | WCAG/ARIA compliance |
| تحسين الأداء (Performance) | React performance optimization |
| كتابة توثيق مشروع | Technical writing، Documentation structure |

## 2. grill-me — الاستقصاء العميق قبل التنفيذ

**الغرض**: قبل تنفيذ أي جزء غامض أو غير موثّق بدقة كافية في `README.md`/`قواعد.md`/`prototype.html`/`design-system.html`/`dev-handoff.md`، لا تفترض ولا تخترع. بدلاً من ذلك، اطرح أسئلة استقصائية متتالية عميقة تكشف حتى التفاصيل التي قد لا تخطر على بالك من أول وهلة.

### مبادئ التطبيق

1. **لا تكتفِ بسؤال سطحي واحد.** الهدف هو تحليل **كل الأجزاء** التي قد لا تكون واضحة، وليس فقط الجزء الظاهر من الطلب.
2. **اطرح الأسئلة بشكل متسلسل ومبني على الإجابة السابقة** — لا تستخدم قائمة أسئلة جاهزة ثابتة. كل إجابة يجب أن تولّد سؤال المتابعة المناسب.
3. **لا تتجاوز عدداً معقولاً من الأسئلة في نفس الوقت** (قاعدة عملية: 3-5 أسئلة كحد أقصى في كل جولة، حتى لا تُثقل على الطرف الآخر).
4. **إذا شعرت بوجود تعارض** بين مصدرين موثقين (مثلاً `قواعد.md` يقول شيئاً و`prototype.html` يُظهر شيئاً مختلفاً) — لا تحسم الأمر بنفسك، اطلب التوضيح صراحة.
5. **المجالات التي يجب دائماً استقصاؤها بعمق عند الغموض** (مستوحاة من منهجية الاستقصاء الشامل): تعريف المشكلة والهدف، الجمهور المستهدف، الهوية البصرية، هيكل الصفحة والمكونات، تجربة المستخدم (User Flow)، قاعدة البيانات والعلاقات، الوظائف (Functions) المطلوبة تحديداً، التكاملات الخارجية، الأمان، الأداء، القيود (ميزانية/وقت/موارد).

### متى تُفعَّل هذه المهارة في QUDRA تحديداً

- عند وجود أي طلب ميزة غير موجودة صراحة في `prototype.html`.
- عند وجود تعارض بين ملفين من ملفات المصدر (راجع تسلسل الأولوية في `README.md`).
- عند طلب حسين لأي تفصيلة لم تُذكر من قبل في أي من ملفات المشروع.
- عند الشك في نية سلوك تفاعلي غير موثّق بوضوح كافٍ (مثال: "ماذا يحدث لو ضغط المستخدم Escape أثناء تحميل بيانات المطابقة؟").

## 4. آلية تحميل مهارة خارجية (عند توفرها)

المعيار المفتوح المستخدم غالباً في هذه المصادر هو تثبيت ملفات `SKILL.md` داخل مجلد مخصص في المشروع (مثال: `.claude/skills/<skill-name>/SKILL.md` أو ما يعادله حسب الأداة)، عبر أمر شبيه بـ:

```bash
npx skills add <repository> --skill <skill-name>
```

**تم التحقق فعلياً** أن Bolt.new قادر على تحميل هذه المهارات بنجاح. عند استخدام أداة أخرى (Claude Code، Cursor، إلخ)، تحقق من توافقها مع نفس الآلية قبل الاعتماد الكامل عليها — وفي كل الحالات، هذا الملف (`SKILLS.md`) يبقى مرجعاً محلياً يعمل بغض النظر عن نجاح أو فشل أي تحميل خارجي.

## 5. مهارات هندسية إضافية موصى بها لمشروع QUDRA

بناءً على طبيعة المشروع (React + TypeScript + RTL + نظام تصميم صارم + معمارية موجهة بالميزة)، هذه فئات مهارات يُنصح بالبحث عنها تحديداً عبر `find-skills` عند تنفيذ المهام المرتبطة بها:

- **مهارات React/TypeScript المتقدمة**: أنماط Hooks المخصصة، إدارة الحالة، الأداء
- **مهارات أنظمة التصميم (Design Systems)**: CSS Custom Properties، Design Tokens
- **مهارات RTL/التدويل (i18n)**: خصوصاً في سياق العربية
- **مهارات الوصولية (Accessibility/WCAG)**
- **مهارات مراجعة الكود (Code Review)**: خصوصاً لضمان الالتزام بمعايير Clean Code الموضحة في `قواعد.md`
- **مهارات كتابة التوثيق التقني**: للحفاظ على جودة تحديثات `TASKS.md`/`CHANGELOG.md`/`DECISIONS.md`

> ملاحظة: هذه فئات مقترحة للبحث عنها عبر `find-skills`، وليست أسماء مهارات مؤكدة موجودة فعلياً — تحقق دائماً من التوفر الفعلي وقت التنفيذ.

## 6. قاعدة ثابتة لجميع الوكلاء

> **لا تفترض. لا تخترع. افحص الموجود أولاً. استخدم Find-Skills قبل التنفيذ. استخدم Grill-Me عند الغموض. نفّذ بأبسط بنية قابلة للتوسع، ثم اختبر كالمستخدم، وتحقق كأدمن، ووثّق كل شيء قبل إعلان الإنجاز.**

قبل كل مهمة:
```text
Task → Inspect → Find-Skills → Select/Activate → Grill-Me if ambiguous → Plan → Execute → Verify → Document
```

لا تعتبر Skill مستخدمة إلا إذا تم تحميلها/قراءتها أو تطبيق تعليماتها فعلياً.
إذا تعذر التحميل، سجّل `UNAVAILABLE` واستخدم القواعد المحلية.

### مهارات يجب البحث عنها بحسب نوع المهمة

| المهمة | ابحث عبر Find-Skills عن |
|---|---|
| React | React best practices / composition |
| Architecture | codebase architecture / domain modeling |
| UI | frontend-design / web-design-guidelines |
| Accessibility | WCAG / accessibility |
| Testing | TDD / verification-before-completion |
| Debugging | systematic-debugging |
| Browser QA | agent-browser / browser-use |
| Supabase | Supabase/Postgres best practices |
| Security | web/app security |
| AI | structured output / prompt engineering / AI engineering |

لا تثبت قائمة مهارات عشوائية على كل مهمة؛ **Find-Skills هو الذي يقرر الأنسب للمهمة**.

## 7. الربط مع `PROJECT_MAP.md`

بعد إتمام أي Task استخدمت فيها مهارة (سواء مُحمَّلة فعلياً عبر `npx skills add` أو مطبَّقة يدوياً من هذا الملف)، سجّل ذلك في إدخال `PROJECT_MAP.md` الخاص بالملف المتأثر تحت "حالات خاصة يجب معرفتها" إن كان لاستخدام تلك المهارة أثر معماري يستحق التوثيق (مثلاً: نمط تصميم معيّن اتُّبع بسبب مهارة محددة). هذا يمنع فقدان سياق "لماذا كُتب الكود بهذا الشكل" عند العودة له لاحقاً.
