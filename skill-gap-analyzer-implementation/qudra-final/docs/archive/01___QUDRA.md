# قُدرة (QUDRA) — فكرة المشروع
## النسخة المرجعية للمشروع

> **الشعار المركزي:** من الكلام إلى الدليل، ومن الدليل إلى الحل.
>
> **المبدأ:** Evidence > Claims / Evidence > CV.
>
> **السؤال الذي تجيب عنه قُدرة:** من قال إنه يستطيع؟ أم من أثبت أنه يستطيع؟

---

## 1. ما هي قُدرة؟

**قُدرة (QUDRA)** هي منصة قائمة على الأدلة (Evidence-Based Problem-to-Team Platform) تربط **المشكلة** بالقدرات البشرية المناسبة، بدل أن تبدأ من السيرة الذاتية أو المسمى الوظيفي.

المنطق الأساسي:

**Problem → Capability → Evidence → Match → Team/Project → Outcome → New Evidence**

قُدرة ليست في جوهرها LinkedIn، ولا منصة عمل حر، ولا منشئ CV، ولا روبوت محادثة عام، ولا أداة عامة لتحليل أفكار الشركات الناشئة.

الفرق الجوهري هو أن نقطة البداية هي **المشكلة**، ثم تحدد المنصة القدرات المطلوبة، ثم تبحث عن أشخاص لديهم أدلة حقيقية على امتلاك هذه القدرات.

---

# 2. المشكلة

الأسواق الحالية تعتمد بدرجة كبيرة على:
- CV.
- Job titles.
- Keywords.
- Self-reported skills.
- شهادات لا تثبت بالضرورة القدرة على التنفيذ.

في المقابل، صاحب المشكلة يريد معرفة:
1. ما القدرات المطلوبة لحل المشكلة؟
2. من يمتلك هذه القدرات فعلاً؟
3. ما الدليل؟
4. ما درجة ملاءمة الشخص للمشكلة؟
5. ما الفجوات الموجودة؟
6. هل يمكن تكوين فريق قادر على التنفيذ؟

قُدرة تنقل عملية الاختيار من **الادعاء** إلى **الدليل**.

---

# 3. الجمهور المستهدف

## A. الشركات والمؤسسات (Companies / Organizations)
تستخدم قُدرة عندما تمتلك:
- مشكلة تقنية.
- مشروعاً يحتاج فريقاً.
- مهمة تحتاج مهارات محددة.
- تحدياً تريد اكتشاف من يستطيع حله.

القيمة:
- تحويل المشكلة إلى متطلبات قدرات.
- اكتشاف المرشحين بناءً على الأدلة.
- تفسير سبب المطابقة.
- معرفة نقاط القوة والفجوات.

## B. المستقلون والمطورون وأصحاب المهارات (Talent / Freelancers / Developers)
القيمة:
- بناء ملف قدرة وليس CV فقط.
- ربط المهارات بأدلة.
- معرفة Skill Gap.
- بناء مسار للوصول إلى دور مستهدف.
- زيادة قابلية اكتشافهم بناءً على ما يستطيعون إثباته.

## C. الطلاب والخريجون (Students / Graduates)
القيمة:
- إثبات القدرة حتى مع خبرة وظيفية محدودة.
- تحويل المشاريع والتحديات إلى Evidence.
- معرفة ما ينقصهم.
- بناء سجل قدرة يتطور بمرور الوقت.

## D. منظمو التحديات والهاكاثونات (Challenge / Hackathon Organizers)
مستقبلاً:
- نشر تحديات.
- استقبال الحلول.
- تحويل النتائج إلى Evidence.
- اكتشاف أصحاب القدرات العالية.

# 4. نموذج المستخدمين

### المستخدم الفردي (Talent)
يدخل → يبني/يربط مصادر الأدلة → تحلل قُدرة ملفه → يظهر Capability Profile → يتم تحديثه مع الأدلة الجديدة.

### الشركة (Company)
تدخل المشكلة → يحللها AI → يستخرج Capabilities → يبحث عن المرشحين → يرى الأدلة → يقارن → يختار.

### النظام (QUDRA Intelligence)
Problem Analyzer + Evidence Analyzer + Matching Engine + Skill Gap Engine + User Intelligence Profile.

---

# 5. الـCore Loop

### المرحلة 1 — Problem
صاحب المشكلة يكتب المشكلة بلغته الطبيعية.

### المرحلة 2 — Capability
AI يحول المشكلة إلى:
- الهدف.
- المستخدم المستهدف.
- القيود.
- المهام.
- القدرات المطلوبة.
- الأولويات.
- التقنيات المحتملة.

### المرحلة 3 — Evidence
قُدرة تجمع/تقرأ الأدلة المرتبطة بالمستخدم.

### المرحلة 4 — Match
محرك المطابقة يقارن:
**Required Capabilities ↔ Proven Capabilities**

### المرحلة 5 — Explain
قُدرة لا تعطي ترتيباً فقط، بل تشرح:
- لماذا تطابق الشخص؟
- ما الدليل؟
- ما نقاط القوة؟
- ما الفجوة؟

### المرحلة 6 — Outcome
بعد التنفيذ تصبح النتيجة دليلاً جديداً.

### المرحلة 7 — Evidence Loop
**Outcome → New Evidence → Stronger Profile → Better Matching**

# 6. الميزات الأساسية

## 1️⃣ Problem Analyzer — محلل المشكلة
يستقبل وصف المشكلة ويستخرج:
- الهدف.
- المشكلة الأساسية.
- نطاق العمل.
- القيود.
- المهام.
- Required Roles.
- Required Skills.
- Required Technologies.
- Priority.

يجب أن يكون الناتج Structured JSON وليس نصاً غير منظم.

---

## 2️⃣ Capability Profile — ملف القدرة
ملف مهني مبني حول ما يستطيع الشخص إثباته.

يتضمن:
- Skills.
- Projects.
- Evidence.
- Challenges.
- Outcomes.
- Sources.
- Confidence.
- Recency.
- Skill gaps.

لا يجب اعتبار CV وحده مصدراً كافياً لإثبات القدرة.

---

## 3️⃣ User Intelligence Profile — الملف الذكي الداخلي
عند انضمام المستخدم وربط الأدلة، تحلل قُدرة المصادر مرة واحدة وتبني ملفاً داخلياً منظماً.

مثلاً:
- Core capabilities.
- Supporting skills.
- Evidence strength.
- Evidence freshness.
- Projects.
- Tools.
- Domains.
- Outcomes.
- Weaknesses / gaps.
- Confidence.

عند البحث عن مرشح لا تعيد قُدرة تحليل كل شيء من الصفر؛ تستخدم الملف المسبق التحليل.

عند إضافة Evidence جديدة:
**New Evidence → Re-analysis → Profile Update → Matching Update**

---

## 4️⃣ Evidence System — نظام الأدلة
مصادر الأدلة المقترحة:
- GitHub.
- Hack The Box.
- Kaggle.
- LeetCode.
- Codeforces.
- HackerRank.
- Projects.
- Certificates.
- Competitions.
- Company Challenges.
- Oral Evidence / AI Interview مستقبلاً.

### ترتيب قوة الدليل
1. Company Challenge.
2. Verified Practical Evidence.
3. External Challenge Evidence.
4. Projects with measurable outcomes.
5. Certificates.
6. Self-claims.

هذا الترتيب ليس حكماً مطلقاً؛ جودة الدليل تعتمد أيضاً على التحقق، الصعوبة، الصلة، الحداثة، والنتيجة.

# 8. GitHub Integration

المسار:
**Connect → Authorize → Select Repositories → Fetch Metadata/Content → Analyze → Evidence Record → Update Intelligence Profile**

التحليل يمكن أن يشمل:
- languages.
- frameworks.
- repository activity.
- commits.
- pull requests.
- issues.
- project structure.
- documentation.
- code quality signals.
- complexity indicators.
- consistency.
- project relevance.

في MVP يفضّل البدء بالمستودعات العامة وبأقل صلاحيات ممكنة.

لاحقاً:
**GitHub Push Webhook → Queue → Re-analysis → Profile Update**

لا نعتمد على اسم المستخدم أو البريد كمفتاح أساسي؛ نستخدم معرفات مستقرة.

---

# 9. Explainable Matching — المطابقة القابلة للتفسير

المعادلة المفاهيمية:

**Match = Required Capability Coverage + Evidence Strength + Relevance + Recency + Confidence − Skill Gaps**

النظام يعرض:
- Match Score.
- Covered capabilities.
- Evidence supporting each capability.
- Missing capabilities.
- Confidence.
- Reasons for ranking.

لا نريد Black Box يقول "95% match" فقط.

---

# 10. Skill Gap — فجوة المهارات

جزء أساسي من MVP.

### للمستخدم
مثال:
**Frontend Developer → Full Stack Developer**

قُدرة تحدد:
- ماذا يمتلك؟
- ماذا ينقص؟
- ما الأولوية؟
- ما المشروع الذي يثبت المهارة الجديدة؟

المسار:
**Learn → Practice → Prove → Re-match**

### للشركة
تظهر:
- strengths.
- missing capabilities.
- impact of gaps on this problem.
- whether the gap is acceptable.

---

# 11. Personalized Roadmap — المسار الشخصي
مستقبلاً/بعد تثبيت الـMVP:
AI يحلل ملف المستخدم كاملاً ويقترح:
- skills to learn.
- projects to build.
- challenges to solve.
- evidence to obtain.
- order of progression.

الهدف ليس "خذ دورة"، بل:
**تعلم → طبّق → أثبت → أعد المطابقة.**

# 26. دروس من Startups.RIP

- Triplebyte: الاختبارات والمطابقة الذكية مفيدة، لكن اقتصاديات السوق ثنائي الجانب واكتساب المرشحين صعبة.
- Gigster: Problem → Plan → Team قوي، لكن إدارة التنفيذ يمكن أن تصبح طبقة تشغيلية مكلفة.
- Codecademy: Learn → Practice → Prove → Match فكرة قوية، لكن لا نريد بناء منصة تعليم كاملة.
- Bits to Atoms: التحقق من المهارات له قيمة، لكن العمل البشري المتخصص قد يصبح قيداً على الهامش.
- CodeStory/Aide: التفوق التقني وحده ليس Moat؛ التوزيع والتركيز مهمان.
- Mindmesh: اتساع المنتج والميزات الكثيرة دون PMF خطر.
- Delve: لا يجوز اختلاق أو تضخيم Claims؛ Evidence يجب أن يكون قابلاً للتدقيق.
- Eventjoy: كون المنتج مفيداً لا يعني أنه شركة مستقلة إذا كان يمكن للمنصة الأساسية تحويله إلى Feature.
- OneGraph: كثرة حالات الاستخدام قد تصعّب البيع.
- Wufoo: Founder-market fit والوصول للجمهور مهمان مبكراً.

# 27. الـMVP الرسمي

إثبات أن QUDRA تستطيع الانتقال من:
**Problem → Capability → Evidence → Explainable Match**

مع **Skill Gap**.

## نطاق MVP

### P0 — ضروري
1. Problem Input.
2. AI Problem Analyzer.
3. Required Capabilities.
4. Seed/User Profiles.
5. Evidence Records.
6. Explainable Matching.
7. Skill Gap.
8. User Intelligence Profile مبسط.
9. واجهة نتائج واضحة.
10. Demo data موثوق.

### P1 — مهم إذا سمح الوقت
11. GitHub Public Repository Analysis.
12. Practical Challenge بسيط.
13. تحديث Evidence بعد نتيجة التحدي.

### خارج MVP
- Full Company Challenge Management.
- Marketplace.
- Payments.
- Full Project Intelligence.
- Full Project Workspace.
- Oral AI Interviews.
- كل integrations الخارجية دفعة واحدة.
- Scraping واسع.

# 28. سيناريو العرض

1. شركة تدخل مشكلة حقيقية.
2. AI يحلل المشكلة.
3. يظهر Required Capabilities.
4. قُدرة تعرض أفضل 5 مرشحين.
5. نفتح Evidence لشخص.
6. نرى لماذا حصل على الترتيب.
7. نعرض Skill Gap.
8. إذا كان جاهزاً: نختاره.
9. إذا نفذ Challenge: يظهر Evidence جديد.
10. يتغير Match/Profile بناءً على الدليل الجديد.

هذه هي القصة التي يجب أن يفهمها الحكم خلال دقائق.

# 32. الأولويات الهندسية

لا نبني Feature كبلوك معزول.

كل Feature يجب أن:
1. يكون قابلاً لإعادة الاستخدام.
2. يفصل UI عن business logic.
3. يفصل business logic عن data access.
4. يستخدم typed models.
5. يملك loading/error/empty/success states.
6. يملك validation.
7. يملك tests مناسبة.
8. يملك security review.
9. يملك UX review.
10. لا يكسر الـfeatures السابقة.

# 33. تعريف الإنجاز Definition of Done

أي Feature لا تعتبر مكتملة حتى:
- تعمل Happy Path.
- تعمل حالات الخطأ.
- تعمل على شاشة صغيرة وكبيرة.
- كل الأزرار تعمل.
- لا توجد dead links.
- البيانات صحيحة.
- لا توجد secrets في frontend.
- صلاحيات قاعدة البيانات صحيحة.
- لا توجد أخطاء Console غير مبررة.
- تم اختبارها كمستخدم.
- تم فحص الكاش وService Worker عند الحاجة.
- تم فحص الأداء الأساسي.
- تم فحص الـresponsive layout.
- تم فحص الهوية والألوان.
- تم تحديث TASKS.
- تم توثيق أي قرار معماري.

---

# 34. الأمن

بعد كل جزء:
- Authentication/Authorization review.
- Input validation.
- Output validation.
- Secrets check.
- API permission check.
- Database Row Level Security عند استخدام Supabase.
- XSS/Injection considerations.
- CORS/configuration review.
- Dependency audit.
- Error messages لا تكشف أسراراً.
- Logs لا تحتوي بيانات حساسة.

الأمن ليس مرحلة أخيرة فقط؛ هو جزء من Definition of Done.

---

# 35. الاختبار

بعد كل Feature:
1. Static/code checks.
2. Unit tests حيث يلزم.
3. Integration tests حيث يلزم.
4. Browser/UI test كمستخدم حقيقي.
5. Keyboard/accessibility sanity check.
6. Responsive test.
7. Network/error-state test.
8. Refresh/deep-link test.
9. Cache/Service Worker test.
10. Regression test.

الهدف:
**ليس أن الكود يبدو صحيحاً؛ بل أن المستخدم يستطيع تنفيذ المهمة فعلياً.**

---

# 36. قاعدة الكود

**Build for the next feature, not only the current screen.**

لا:
- giant component.
- duplicate logic.
- hard-coded design values.
- API calls داخل كل component.
- business logic داخل JSX.
- state global بلا داعٍ.
- secrets في client.
- temporary hacks دون TODO واضح.

نعم:
- reusable components.
- feature-based modules.
- typed contracts.
- services/repositories.
- centralized design tokens.
- validation.
- predictable state.
- tests.
- documentation.

---

# 37. قاعدة الكاش

يجب تحديد سياسة Cache لكل مصدر.

خصوصاً:
- Service Worker.
- API responses.
- static assets.
- authentication/session.
- Supabase data.

لا يجوز أن يؤدي Cache إلى عرض بيانات قديمة أو روابط backend قديمة.

بعد deployments:
- verify build.
- verify environment.
- unregister stale Service Worker عند الحاجة.
- test hard refresh.
- test clean session.
- test fresh browser.

---

# 38. الرؤية بعيدة المدى

قُدرة يمكن أن تتحول من منصة مطابقة إلى:
**Capability Intelligence Infrastructure**

أي نظام يعرف:
- ماذا تحتاج المشكلة.
- من يستطيع تنفيذها.
- ما الدليل.
- ما مستوى الثقة.
- ما الفجوة.
- كيف نبني الفريق.
- ماذا تعلمنا من النتيجة.

والميزة الأهم:
كل تنفيذ ناجح ينتج Evidence جديداً.

---

# 39. ما الذي لا يجب فعله

- لا نحول QUDRA إلى LinkedIn.
- لا نبني Marketplace قبل إثبات core.
- لا نبني Project Intelligence قبل تثبيت evidence matching.
- لا نجمع عشرات integrations قبل بناء Evidence Model قوي.
- لا نعطي scores بلا تفسير.
- لا ندعي التحقق إذا لم نتحقق.
- لا نعتبر certificate مساوية لتحدٍ عملي حقيقي.
- لا نبني نظاماً ضخماً في 10 أيام.

---

# 40. مبدأ القرار

عند أي Feature جديدة نسأل:

**هل تقوي Evidence → Capability → Match؟**

إذا نعم: أولوية أعلى.

إذا كانت تساعد الـworkflow مستقبلاً: Backlog.

إذا كانت مجرد Feature جذابة ولا تقوي القيمة الأساسية: لا تدخل MVP.

---

# 41. تعريف نجاح MVP

ينجح MVP إذا استطاع في Demo حقيقي:
- استقبال مشكلة.
- فهمها.
- استخراج القدرات.
- عرض أشخاص لديهم Evidence.
- تفسير المطابقة.
- كشف Skill Gap.
- إظهار أن Evidence أقوى من Claim.

هذا أهم من عدد الشاشات أو عدد integrations.
